# Configuration

- Externalize configuration. The same build behaves differently per environment through values, not code branches.
- `.env` holds environment values and is bundled as an asset. `.env.example` documents every key (name, meaning, example). Update both when adding a key.
- Access config through one typed place (`lib/core/env.dart`), never `dotenv.env['X']` scattered across features. Each value is a typed getter with a clear name.
- Fail fast on missing or invalid config at startup (`main.dart`), not at first use. A missing `SUPABASE_URL` should stop the app with a clear message before any screen builds.
- No hardcoded URLs, bucket names, timeouts, limits or thresholds in feature code. Business constants (max photos, max photo bytes, field length limits) are named constants in the owning feature's domain, referenced by both validators and rules docs.
- Sensible defaults for tuning values. No defaults for secrets.
- Keep environments minimal. If a dev/prod split appears, it is a separate `.env` file or `--dart-define-from-file`, not `if (kDebugMode)` branches in business code.
- Firebase configuration is generated by FlutterFire (`firebase_options.dart`, `google-services.json`). Regenerate it with the tool; never hand-edit.
- Use feature flags only for risky or incomplete behavior, keep them in config, and delete them when done.
- Document each config key in `.env.example` and nowhere else, so there is one source.
